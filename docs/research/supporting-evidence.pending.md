### #97 — the RP2350 cross-ISA substrate: one signed table, byte-identical decisions on the ARM Cortex-M33 AND the RISC-V Hazard3 cores of the same chip, 124/124 each (August 2026)

**Claim:** the same certified `.ppt` images every other substrate holds are decided byte-identically by a Raspberry Pi Pico 2 (RP2350) on BOTH of its instruction-set architectures — the ARM Cortex-M33 core and the Hazard3 RISC-V core — from ONE source file, each certifying 124/124 on the declared subset. This is cross-ISA conformance on a single chip, a dimension no other substrate on the ladder covers (the language kernels are cross-language on one ISA; this is one source across two ISAs of one die).

**Method:** `prismpath-hw/rp2350/ppt_rp2350.c` is a byte-exact copy of `interp.c` / `ppt_uno.c`'s evaluator core (typed-comparator atoms over the field register file, RPN edge programs with the five boolean opcodes, first-true-edge priority encoder); only the I/O layer differs from the AVR (#92) — native USB-CDC via the Pico SDK instead of the AVR UART. The ISA identifier is chosen by the compiler (`#if defined(__riscv)`), so the SAME source self-identifies as `rp2350-arm` or `rp2350-riscv`. Built twice from one CMake project: `-DPICO_PLATFORM=rp2350-arm-s` (Ubuntu gcc-arm-none-eabi 13.2) and `-DPICO_PLATFORM=rp2350-riscv` (the Raspberry Pi `riscv32-unknown-elf` newlib toolchain, gcc 15.2 — Ubuntu's own riscv gcc lacks newlib's `nosys.specs`). Certified with `certify_rp2350.py`: the EXACT contract of `run_vectors.cert_predicates` with the subprocess replaced by the USB-CDC wire — each in-subset predicate compiled by the UNTOUCHED compiler, streamed ('L'), the registers from the UNTOUCHED `encode_regs` streamed ('V'), the board's verdict checked against the frozen expectation; exclusions by the same machine-readable reasons.

**Result:** **ARM Cortex-M33: 124/124 pass, FAIL 0; RISC-V Hazard3: 124/124 pass, FAIL 0** — both against corpus v2 (1,079), both with all **955 exclusions itemized under byte-identical reasons** (281 field-vs-field + 251 disallowed + 141 constant-only + 119 string-ordering + 114 non-literal-collection + 36 substring + 11 non-scalar + 1 nested + 1 float). USB-CDC eval round-trip: ARM 146/298/1594 µs, RISC-V 139/345/1576 µs (min/median/max) — wire-dominated, an order of magnitude under the AVR's 38400-baud serial; the point is the decision executes ON the MCU core, on each ISA, from the same signed bytes. **Honest scope:** predicate/single-hop decisions only — engine-vector (multi-hop) replay and the visits bank are the same declared non-goals as the AVR tier (#92). Provenance: `prismpath-hw/rp2350/` (`ppt_rp2350.c`, `CMakeLists.txt`, `Makefile`, `certify_rp2350.py`, `cert_rp2350_arm.json`, `cert_rp2350_riscv.json`); Pico SDK 2.1.1; RPi riscv-toolchain v2.3.0-0 (gcc 15.2, newlib).

### #98 — the Xtensa substrate: the same signed table certified on an ESP32 (ESP-WROOM-32, Xtensa LX6), 124/124 — a third MCU ISA, four in total (August 2026)

**Claim:** the same certified `.ppt` images are decided byte-identically by an ESP32 (ESP-WROOM-32, dual-core Xtensa LX6) — 124/124 on the declared subset — adding **Xtensa** as a third distinct MCU instruction set. Four MCU ISAs now decide the same signed policy identically: 8-bit AVR (#92), ARM Cortex-M33 and RISC-V Hazard3 (#97), and Xtensa LX6.

**Method:** `prismpath-hw/esp/main/ppt_esp32.c` — the byte-exact evaluator core (identical to `interp.c` / `ppt_uno.c` / `ppt_rp2350.c`); only the I/O differs: the ESP-IDF UART driver on UART0 (the CP2102 bridge) with the console and all logging disabled (`sdkconfig.defaults`) so nothing corrupts the binary wire, and UART0 pinned explicitly to GPIO1/3 (with the console off, IDF does not route the pads — the bug that first showed as boot-log-but-no-reply). The firmware is target/ISA-generic: the ident and pins are chosen at compile time (`CONFIG_IDF_TARGET`, `__XTENSA__` / `__riscv`), so one project certifies `esp32` (Xtensa) or `esp32c6` (RISC-V). Built with ESP-IDF v5.4 (xtensa-esp-elf gcc 14.2). Certified with `certify_esp32.py` — the `run_vectors.cert_predicates` contract over the UART wire, each in-subset predicate compiled by the UNTOUCHED compiler and its regs from the UNTOUCHED `encode_regs`; a DTR/RTS reset-into-app sequence handles the dev board's auto-reset-on-open.

**Result:** **124/124 pass, FAIL 0** (`ppt-esp32/1 esp32-xtensa PPTM-v1`) against corpus v2 (1,079), all **955 exclusions itemized under byte-identical reasons** (281 field-vs-field + 251 disallowed + 141 constant-only + 119 string-ordering + 114 non-literal-collection + 36 substring + 11 non-scalar + 1 nested + 1 float). UART eval round-trip 2268/3441/5258 µs (min/median/max) — higher than the RP2350's USB-CDC because this is a real 115200-baud UART; the point is the decision executes on the Xtensa core from the same signed bytes. **Honest scope:** predicate/single-hop only — the same declared non-goals as the other MCU tiers (#92, #97). Provenance: `prismpath-hw/esp/` (`main/ppt_esp32.c`, `certify_esp32.py`, `cert_esp32.json`, `sdkconfig.defaults`); ESP-IDF v5.4, xtensa-esp-elf gcc 14.2; board ESP-WROOM-32.

### #99 — on-device sensor → decision: the RP2350 reads a real VL53L0X and routes the signed Level M policy live (August 2026)

**Claim:** beyond the substrate certs (where the host feeds register values), the RP2350 reads a real **VL53L0X time-of-flight sensor** over I2C, forms the field vector itself, and runs a signed Level M proximity policy **on-device** — distance routes to a band (contact/near/mid/far) live, with no host in the loop. The routed decision flips **exactly at the policy's authored thresholds** (100/300/800 mm), from the same compiler and byte-exact evaluator every substrate certifies. This is the first physical-input demonstrator since the FPGA fabric — the ToF standing in for the not-yet-arrived IMU.

**Method:** `prismpath-hw/rp2350/ppt_tof.c` bakes a compiled `.ppt` into flash — the proximity policy (`dist_mm` → contact/near/mid/far, generated by `gen_proximity_table.py` from the UNTOUCHED compiler, emitted as `table_proximity.h`) — reads the sensor via a compact Pico SDK I2C driver (`vl53l0x.c`, a port of the Pololu init + single-shot sequence), sets field 0 = distance, runs the byte-exact evaluator, and reports the band over USB-CDC. Built as a second target in the RP2350 CMake project; I2C at 100 kHz on GP4/GP5. A start-up + failure-path I2C bus scan makes wiring self-diagnosing.

**Result:** live on hardware — the band tracks distance in real time, transitioning at the authored boundaries: **contact** observed 48–88 mm (< 100), **near** 104–290 mm (100–300), **mid** 403–733 mm (300–800), **far** at out-of-range (≥ 800 / no target). The on-device evaluator respects the signed thresholds exactly. **Honest scope:** a demonstrator, not a certified conformance sweep — one field, single-hop, and the ranging accuracy is the VL53L0X's (the *decision* is exact given the reading). Provenance: `prismpath-hw/rp2350/` (`ppt_tof.c`, `vl53l0x.c/.h`, `gen_proximity_table.py`, `table_proximity.h`); board Raspberry Pi Pico 2 W (RP2350).

### #100 — coordinated fleet policy-swap: one table pushed to three ESP32s over ESP-NOW, verified per-node, committed in two phases, flipped together (August 2026)

**Claim:** three independent ESP32 nodes, each running the byte-exact evaluator, swap from a permissive policy to a tightened one **together** on command — the change is broadcast once, **re-verified on every node before it is staged** (each follower re-hashes the received table and checks the id against an on-device allowlist; a table that does not match is refused, not swapped), committed only after a quorum of nodes acknowledges, and applied at a shared tick so the whole fleet flips within sub-millisecond of the others. This is the multi-node analogue of the single-node hot-swap (#87/#88): the same "verify-then-swap, refuse-don't-downgrade" contract, extended across a mesh with a two-phase commit so no node flips alone.

**Method:** `prismpath-hw/mesh/` — three ESP-WROOM-32 boards flashed with `ppt_mesh.c`, all carrying two compiled `.ppt` images baked to flash (`gen_mesh_tables.py` → `tables.h`: **policy A** `level < 300` permissive, **policy B** `level < 200` tightened, each 84 bytes, each tagged with its FNV-1a-32 id — `A=0xb3d16ba0`, `B=0xa4fdc82f`). Nodes gossip status and coordinate over **ESP-NOW** (connectionless broadcast, no AP). Poking one node over USB with `R` makes it coordinator; it runs a two-phase commit: **PREPARE** broadcasts the target table + id → each follower recomputes `fnv1a32(received)` and checks it equals the announced id **and** the id is in its baked allowlist `{A,B}`; only then does it stage the table and **ACK** → the coordinator waits `ACK_WIN=500 ms` and proceeds only with a quorum (2 ACKs), else **ABORT** → **COMMIT** carries a `FLIP_DELAY=120 ms`; every node applies the staged table at *its own* `local_now + 120 ms`, so the flip lands together without a shared global clock. A host script (`orchestrate.py`) opens all three ports, triggers the rollout, and timestamps every node's flip.

**Result:** reproducible live — baseline all three at `active=A verdict=ALLOW epoch=0` (at the test field `level=250`, policy A → ALLOW); after one `R`, the log shows `PREPARE seq=1 target=B` → both followers `PREPARE ok … staged — ACK` → coordinator `2 ACKs — COMMIT` → all three `FLIP → policy B verdict=DENY epoch=1`, then steady `active=B verdict=DENY epoch=1`. Host-observed flip spread across the three nodes: **0.7 ms** (3/3 flipped) — and that includes USB-serial read jitter, so the on-device spread is tighter. **Honest scope:** a demonstrator, not a certified sweep. The per-node check is an **FNV-1a-32 id/allowlist** (fast integrity + pre-vetting), standing in for a real signature — **Ed25519-on-the-mesh is the named follow-on**, at which point the check becomes cryptographic rather than integrity-only; the two-phase quorum is fixed at 2 followers; and "simultaneous" means *commit + fixed local delay* (bounded by ESP-NOW receipt jitter and negligible same-MCU clock skew over 120 ms), not PTP-style clock sync. Provenance: `prismpath-hw/mesh/` (`ppt_mesh.c`, `gen_mesh_tables.py`, `main/tables.h`, `orchestrate.py`); three ESP-WROOM-32 boards; ESP-IDF v5.4.
