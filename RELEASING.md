# Releasing PrismPath to PyPI

This page says how a release is built and checked, which repository it comes from, and what the owner has to
decide. It separates what the files and PyPI itself show from what is only remembered or still open.

## What is known

**PyPI holds one release, 0.1.0, uploaded on 2026-08-17 at 12:39 UTC (a wheel and an sdist, one second
apart).** It was built from this repository, `crystal-warden/prism-path`, and not from the product mirror
`crystal-warden/prismpath`. The evidence, from downloading the sdist and comparing it with each line:

- Every file in the sdist (all the `prismpath/` sources, the docs, `pyproject.toml`, `tools/mirror_readme.md`)
  is byte for byte the file at commit `6cafd86` of this repository (2026-08-17 01:19 CDT, "mirror: lean,
  verified product README via a source template"). The one sdist file with no counterpart in git is
  the generated architecture scorecard (`arch-scorecard.md` under `docs/design`), which `.gitignore` lists. A later commit
  (`3bbc91c`, 07:48 CDT) touches only evidence files, so the upload may have been built at either; the
  package contents are the same.
- The sdist carries `docs/research/` and `tools/mirror_readme.md`. The mirror excludes both
  (`tools/export_clean.py`, `EXCLUDE_PREFIXES` and `EXCLUDE_EXACT`), so the sdist cannot have come from it.
  Against the mirror's `9129c27` (the same day, "lean product-mirror README") the sdist differs in five
  documents and carries six files the mirror lacks.
- It was not built at the `v0.1.0` tag. The tag is `990f493` (2026-08-05), 253 commits earlier than `6cafd86`;
  134 files under `prismpath/` differ between the tag and the PyPI sdist. The README's `git archive ... v0.1.0`
  checksum and its OpenTimestamps proof therefore describe the tag, not the files on PyPI.
- The PyPI page's `Homepage` points at the mirror, and `Repository`, `Getting Started`, `Specification`,
  `Changelog` and `Security` point at this repository. That is `pyproject.toml` as of `6cafd86`.

**Neither repository can publish today.** There is no publish workflow anywhere:

| Repository | Workflows | Publishes to PyPI |
|---|---|---|
| `prism-path` (this one) | `ci.yml`, `formal.yml` | no |
| `prismpath` `main` (mirror) | `ci.yml` (generated by `export_clean.py`) | no |
| `prismpath` `product/seed-2026-09-19` | `ci.yml` | no |

None of them uses `pypa/gh-action-pypi-publish`, `id-token: write`, `twine` or a token secret (checked with
`grep` in all three trees and through the GitHub workflows API for both public repositories). PyPI shows no
PEP 740 attestation for either 0.1.0 file (the provenance endpoint returns 404), which a Trusted Publishing
upload would have. The owner's recollection and earlier session records say 0.1.0 was uploaded by hand with
`twine upload dist/*` and an API token (username `__token__`) from a local virtualenv. Everything here fits
that, and a manual upload is the only mechanism that exists. Run it from whichever checkout you built in;
PyPI does not know or care which repository it came from.

## The three lines

| Line | Where | What it is |
|---|---|---|
| Research repo | `crystal-warden/prism-path`, `main` | The source of truth: the package, the research, the evidence ledger, the hardware. `pyproject.toml` here is the one 0.1.0 came from. |
| Mirror, `main` | `crystal-warden/prismpath`, `main` | A generated subset. `python tools/export_clean.py --out ../prismpath-clean` rebuilds the tree from this repository and never commits or pushes. Its last full export was 2026-08-17 (`a3de376`, `9129c27`); four documentation commits followed on 2026-11-04. Re-running the export now would change about 460 of its 540 files, so the mirror's `main` is far behind this repository. |
| Product branch | `crystal-warden/prismpath`, `product/seed-2026-09-19` (tip `a86546c`, 2026-10-13) | Not an export. It was seeded from research commit `40a9b05` on 2026-09-19 and has been advanced by its `promote` tool (last: research `a0cccf8`). It has its own `pyproject.toml` (different description, `README.md` as the PyPI page, no `comparisons` extra, links only to the mirror and a `Research` link), `PROVENANCE.md`, `COMPATIBILITY.md`, `DIVERGENCES.md`, and a release gate (the `release_eligibility` tool and `release_policy` flow in its `tools/` directory) whose receipt says an artifact "may be offered for the owner's release decision". It intentionally differs from research: `prismpath compile` is withdrawn, the JavaScript port and playground are not carried, and it carries a few product only fixes (`DIVERGENCES.md` lists them). It has not received the 2026-11-04 cleanup commits. |

The export script and the product branch are two different ways of producing a "clean" repository. The
export script is a one way copy that was used once; the product branch is a maintained fork with a
provenance system. Nothing in either repository says which one is meant to be the release source.

## Building and checking a release

From a clean checkout of the commit you intend to release:

```bash
python3 -m venv /tmp/rel && /tmp/rel/bin/pip install build twine
/tmp/rel/bin/python -m build --outdir /tmp/rel/dist     # sdist and wheel
/tmp/rel/bin/twine check /tmp/rel/dist/*                # metadata and README render
python3 -m venv /tmp/rel-smoke && /tmp/rel-smoke/bin/pip install /tmp/rel/dist/*.whl
cd "$(mktemp -d)" && /tmp/rel-smoke/bin/prismpath init && /tmp/rel-smoke/bin/prismpath validate flow.md \
  && /tmp/rel-smoke/bin/prismpath test flow.md
```

The PyPI page is rendered from `tools/mirror_readme.md` (`readme` in `pyproject.toml`), not from `README.md`,
so edit that file when the install instructions change. `build` needs `setuptools>=77` (it reads the SPDX
license expression and `license-files`). The version is the one `version =` line in `pyproject.toml`;
PyPI refuses a version it already has, so bump it before building.

Before uploading, the owner will want the gates CI runs (`python -m pytest prismpath/tests -q` and
`python -m prismpath.safety.fuzz_predicates -n 20000`) green on the commit, a changelog entry moved from
`[Unreleased]` to the version, and a tag. Then, with the owner's own account:

```bash
twine upload --repository testpypi /tmp/rel/dist/*     # optional rehearsal, a separate token
twine upload /tmp/rel/dist/*                           # username __token__, password the PyPI API token
```

A PyPI file can be yanked but never replaced, so a bad upload costs a version number.

## What switching the release source would take

PyPI projects are not tied to a repository, and the 0.1.0 uploads used a token, so **changing the source needs
no PyPI setting change.** Check out the other repository at the commit you want, build there as above, and
upload with the same token (or a new project scoped token). What it does change is the contents, the metadata
and the links:

- **Release from this repository** (what 0.1.0 did). Pros: it is the source of truth, the package is whatever
  CI tests here, `pyproject.toml` already names it, and no step can drift. Cons: the sdist carries the
  `docs/research/` papers and the `tools/` directory, and it ships the research repo's wording and the
  `comparisons` extra.
- **Release from the mirror's `main`.** It would need an export run first (`export_clean.py`), then a
  decision to commit the result, because the mirror has not been regenerated since August. The sdist would
  lose the research documents. As it stands the mirror's `main` cannot be built at all: its `pyproject.toml`
  says `readme = "tools/mirror_readme.md"`, and the export leaves that file out (it is the source of the
  generated `README.md`), so the build would fail on a missing readme until the export handles it. Cons: a
  generated copy of the tested source rather than the source itself.
- **Release from the product branch.** It is the line built for being "the product" (provenance, divergence
  list, compatibility promise, a release gate), and its package metadata is self contained. Cons: it is a
  different build of the package, with `compile` withdrawn and no JavaScript engine, so what a user gets
  differs from 0.1.0; its history is the mirror's, not this repository's; and research changes after
  `a0cccf8` reach it only through a promotion.

If the owner wants uploads to come from a workflow instead of a laptop, that is new work in whichever
repository is chosen: a workflow with `permissions: id-token: write` that runs `python -m build` and
`pypa/gh-action-pypi-publish`, and, on pypi.org, **Manage, Publishing, Add a new publisher** with the owner
of the repository, the repository name, the workflow file name and an optional environment. To move an
existing trusted publisher, add the new repository's entry and remove the old one. None of that exists yet,
and no workflow in this change creates it.

## Decided (2026-11-04)

1. **Release source: the mirror's `main`, freshly exported.** Run `python tools/export_clean.py --out
   ../prismpath-clean` from this repository at the commit being released, review and commit the result in the
   mirror, then build and upload from the mirror checkout as above. The export copies `tools/mirror_readme.md`
   into the mirror unchanged, because `pyproject.toml` names it as the PyPI page.
2. **Version: 0.1.3,** the first upload since 0.1.0. Two tags were pushed and superseded before any upload: `v0.1.1`
   (2026-11-04), when a hand check of every documented capability found 14 bugs and the receipt signing gap, and
   `v0.1.2` (2026-11-05), when the owner chose to ship its follow-ups and the Rust verifier in the same upload rather
   than upload twice in a day. PyPI never held 0.1.1 or 0.1.2.
3. **Uploads stay manual,** with `twine` and the owner's API token. No publishing workflow is added.

4. **Tag and timestamp.** Tag the released research commit and the mirror commit `v0.1.2`, write the
   SHA-256 of the exact wheel and sdist that are uploaded to a `SHA256SUMS` file, and stamp it with `ots stamp`.
   Upload those same files, because a rebuild is not byte identical and the proof would not match it.
