# PrismPath in F Prime

The same decision and receipt core as [the cFS app](../cfs/README.md), as an F Prime component in a small reference
deployment. It is work package S4 of [the flight software plan](../../docs/design/cfs-app-plan.md). Its check is the
cross framework claim: the same proposals give the same decisions and the same receipts, byte for byte, in both
frameworks, because both run the same C.

This integration was written with AI assistance (Claude). Nothing in it has been offered to the F Prime project. F Prime
asks contributors to say how generative AI was used, and anything offered upstream would say so.

```
Proposer --proposalOut--> Guard --comOut--> cmdDisp.seqCmdBuff --> Vehicle.ACTUATE      (allowed only, after the receipt)
(ground command)             |
                             +--> events: Allow, Refuse (registered cause), Escalate (registered cause)
                             +--> telemetry: the counters, the receipt count
                             +--> a signed core run in RUN_DIR (receipts, root statement) for the ground to verify
```

## What is here

| Path | What it is |
|---|---|
| `PrismPathRef/Guard` | The component. `Guard.fpp` and `Guard.cpp` are the F Prime side, `GuardCore.c` the glue to the shared C. |
| `PrismPathRef/Proposer` | A stand in for an autonomy function: a ground command that sends a proposed command packet to the guard. |
| `PrismPathRef/Vehicle` | A stand in for the vehicle: `ACTUATE`, the command the guard protects. |
| `PrismPathRef/Top`, `Main.cpp` | The deployment, generated by `fprime-util new --deployment` (F Prime's own template, TCP client, with its core subtopologies) and extended with the three components and their connections. |
| `ground/provision.py` | Makes the two test keys and the signed policy table the guard loads. |
| `ground/conform.py` | The byte comparison with the cFS app's receipts. |
| `tests/` | The end to end run, its F Prime integration test, and the checks that need only a C compiler. |

The guard does not copy the cFS app's code. `PrismPathRef/Guard/CMakeLists.txt` compiles, from where they live,
`integrations/cfs/prismpath_app/fsw/src/prismpath_app_kernel.c` (the decision core over `prismpath-hw/ppt_eval.h`) and
`prismpath_app_run.c` (the receipts over `prismpath-ebpf/merkle.h`), plus the Monocypher in `prismpath-hw/mesh/main`. The
one change made under `integrations/cfs` is that `PP_RUN_DECIDER`, the name every receipt carries for who decided, can
be defined by the build (`prismpath_app_run.h` defaults it to `cfs:prismpath_app` as before). F Prime's build only
compiles sources under its own build roots, so those four files are a plain CMake library, `prismpath_core`, that the
component links. F Prime's framework itself is used in place from `.cfs-build/fprime` (see `settings.ini`) and none of
its code is copied here.

## How it decides

The Proposer's `PROPOSE` command builds the serialized command packet for `Vehicle.ACTUATE` (descriptor, opcode, then the
arguments `cmd_class`, `ground_contact`, `slew_deg`, `thrust_pct`) and sends it to the Guard, never to the dispatcher.
The Guard reads the packet as the dispatcher would, takes its argument bytes, and puts each field the arguments hold
completely at its offset in the policy's layout ([`prismpath_app_layout.h`](../cfs/prismpath_app/fsw/inc/prismpath_app_layout.h)):
F Prime serializes big endian and the cFS payload is little endian, so a two byte field is reversed. A packet that ends
before a field is then the core's own `missing` refusal, as a short cFS payload is (`PROPOSE_PARTIAL` sends one).

The payload goes through `PP_Kernel_Decide` and `PP_Run_Record`, exactly as in the cFS app: the decision is receipted
first, a decision that cannot be receipted is not acted on, an allowed command is forwarded to `cmdDisp.seqCmdBuff`
unchanged (its bytes are the ones that were decided), and a refused or escalated one is not. The dispatcher then
dispatches it to `Vehicle.ACTUATE`. With no active policy every proposal is refused (cause 32) and nothing is receipted.

The policy comes from a file named by a parameter. The Guard's parameters are `POLICY_FILE`, `KEYS_DIR` and `RUN_DIR`
(defaults `pp/pp_policy.tbl`, `pp` and `pp/run`, relative to the deployment's working directory; F Prime limits a parameter
string to `FW_PARAM_STRING_MAX_SIZE`, 40). The `LOAD_POLICY` command reads the table (the raw bytes of `PP_PolicyTable_t`,
or a cFE table file, which has 116 bytes of headers first), `pp_authority.pub` and `pp_instance.key` from `KEYS_DIR`, runs
the cFS app's own checks (the kernel's structural checks, the authority's two signatures, the version floor) and makes it
active. A refusal is an event with the registered cause code and leaves the active policy as it was. `SEAL` signs a root
statement over every receipt onboard with the instance key and writes the run, in the core run layout the ground's
verifier reads. `REPORT` sends the counters as an event.

## Build and run

You need a C and C++ compiler, CMake 3.26 or newer, OpenSSL development files (the receipts' SHA-256 is OpenSSL's, as in
the cFS app) and an F Prime checkout (Apache-2.0). `settings.ini` expects it at `.cfs-build/fprime` at the repository
root, which is gitignored; `settings.ini` and `CMakeLists.txt` hold the path if yours is elsewhere. F Prime's tools go in
a virtual environment of their own, at the versions the checkout pins:

```
python3 -m venv .cfs-build/fpvenv
.cfs-build/fpvenv/bin/pip install -r .cfs-build/fprime/requirements.txt
```

Build the deployment (this was done with F Prime v4.4.0 plus its development commits):

```
cd integrations/fprime
PATH=$PWD/../../.cfs-build/fpvenv/bin:$PATH fprime-util generate
PATH=$PWD/../../.cfs-build/fpvenv/bin:$PATH fprime-util build
```

If `cargo` is on your `PATH`, F Prime also builds its Rust WASM sequencer, which cargo refuses inside this repository's own
Cargo workspace. Take `cargo` off the `PATH` for these two commands (F Prime then skips that component) or build from a
checkout outside the workspace.

Run the scenario, headless (about a minute):

```
python3 integrations/fprime/tests/run_scenario.py        # with the repository's Python environment, which has the signing extra
```

It provisions a scratch directory, starts the GDS without a GUI (`fprime-gds -g none -n`), starts the deployment from the
scratch directory so the guard's relative paths are there, and runs `tests/gds_scenario.py` with pytest and F Prime's
integration test API (`fprime_test_api`). That test

1. proposes a command with no policy loaded: refused with cause 32, not receipted;
2. sets `KEYS_DIR`, `RUN_DIR` and `POLICY_FILE` (a table with one threshold changed and not signed again) and loads it:
   `PolicyRejected` with cause 2 (`sig:invalid`);
3. sets `POLICY_FILE` to the signed table and loads it: `PolicyLoaded` for version 2;
4. proposes the 13 commands of the S1 sequence in [`integrations/cfs/tests/run_scenario.py`](../cfs/tests/run_scenario.py)
   through the Proposer, and checks each `Allow`, `Refuse` or `Escalate` event, its cause and its receipt number against
   the Python reference decision on the same reading, and that exactly the allowed commands reach `Vehicle.ACTUATE`
   through the dispatcher, in order, with their arguments;
5. seals the run.

Then, on the ground, it copies the run directory out and holds it to the cFS app's receipts (below), runs the repository's
verifier on it with both keys pinned and every receipt replayed through the reference kernel, and checks that the root in
the `Sealed` event is the run's root. The same verification by hand:

```
prismpath evidence verify <run> --sample all --pin-authority <keys>/authority.pub --pin-instance <keys>/instance.pub
```

## The conformance claim, and its one difference

The two frameworks' receipts differ in one member. Every receipt names who decided it, and the cFS app's is
`cfs:prismpath_app` where the guard's is `fprime:prismpath_guard`. Everything else (the case, the image hash, the
reading hash, the decision, the order) is identical byte for byte, and `ground/conform.py` checks exactly that: it
replaces the one string and compares the lines. Built with the cFS name (the shared header's default), the same C writes
the cFS app's receipts with no difference at all, which `tests/test_fprime_conformance.py` shows.

"The cFS app's receipts" are the Python reference writer's, `integrations/cfs/ground/reference.py`, to which
`integrations/cfs/tests/test_cfs_run.py` holds the cFS app's C line by line. A real cFS run can be compared directly with
`python -m integrations.fprime.ground.conform <guard run> --cfs-run <cFS run>`; no cFS build was run for this work.

`tests/test_fprime_conformance.py` needs only a C compiler and OpenSSL. It compiles `GuardCore.c` with the shared C and
plays the S1 sequence, every truncation of one proposal and a grid across the policy's thresholds (310 proposals) through
the guard's own reading of F Prime's serialized arguments. It checks every decision against the reference, every receipt
against the cFS app's bytes, the run with `prismpath evidence verify`, a tampered table refused as `sig:invalid`, and a
cFE table file loading like the raw table. `tests/test_fprime_run.py` runs the end to end scenario above and skips,
saying why, without an F Prime build.

## What it shows

- One policy, one decision core and one receipt format give the same evidence in two flight software frameworks.
- The guard sits on a real F Prime command path: a proposed command packet goes to a component, and only an allowed
  one reaches the command dispatcher.
- The policy loads from a file named by a parameter, and a table the authority did not sign never decides.
- The ground verifies the run with the same verifier and pinned keys as for the cFS app.

## What it does not show

- It does not make the guard unavoidable. F Prime's command dispatcher has no access control, so a ground command for
  `Vehicle.ACTUATE` sent straight to the dispatcher bypasses the guard. Here the guarded path is the Proposer's. A
  deployment that wants every command guarded routes its sources (the uplink router, the sequencer) through the guard and
  does not let them reach the dispatcher; that wiring is not built here.
- It does not survive a processor reset. The cFS app keeps its Merkle peaks and its version floor in the Critical Data
  Store. F Prime has no such store, so the guard's run state is in memory: after a restart it begins a new run with no
  floor. A deployment would keep that state in its own non volatile storage.
- It is not flight hardened. The guard is passive and runs on the thread of whoever calls it, its files go through stdio,
  the keys are test keys in the file system, and the run is sealed only on a ground command.
- It does not run on a target. It is built and run on Linux (aarch64 here). The SHA-256 is
  OpenSSL's; a flight target supplies its own through `PPT_MERKLE_SHA256_EXTERNAL`, as for the cFS app.
- It does not read typed command arguments past the layout. The policy's fields are the four arguments of one command;
  another command needs its own layout and policy.
- The Proposer and Vehicle are stand ins. The Vehicle records what it was commanded and does nothing else.
- No F Prime unit tests (UT) are included, and F Prime's googletest submodule is not needed to build this.
